连着几个版本，我一次次找到同一件事，每次都当成巧合：runtime 记下了某个事实，而没有任何东西读它。一个
被两个投影器 fold、却没有任何东西发出的矛盾事件。一份每次仓库状态查询都要算、而没人读的移动报告。两个
在六十处被认真写下、没人读的 capability 字段。每次写入的 receipt 上都盖着「这个文件之前存不存在」的标志
位，没人读。

五次不是巧合。所以我去找成因，找到的是一个接口。

### 八十四分之二

四个环境 provider 里，承载「我刚做了什么」的对象字面量一共有 **84 个不同的键**。而把这些事实带进 runtime
自身推理的那个抽取器，读其中 **2 个**：`path` 和 `digest`。

其余的一切——文件是被创建还是被覆盖、它先前的摘要、应用了几处编辑、字节长度、仓库的 diff 摘要——都抵达了
抽取器，然后没有被带过去。而这个窄是刻意的，理由就写在原地：

> 一个想让自己的资源被追踪的 provider 说 `path` 和 `digest`；这就是全部契约。

理由是：任何更宽的东西都是「一个没人同意过的 schema」。

所以那五个发现不是疏忽在累积。**它们是这条纪律的产物**，而且它还会继续产出。两半同时为真：更宽的契约会
让一个有用的事实抵达那条能用它的规则，同时也正是这份契约所拒绝的、被发明出来的 schema。

这个重构比那五个发现里的任何一个都值钱。但它也引出了一个更尖的问题：如果一个被记录的事实可能到不了消费者，
那这棵树里还有什么是**存在而不可达**的？

### 百分之二十一

这棵树只发布一个二进制。从它的入口出发做模块导入的传递闭包，167 个生产模块里：**132 个可达，35 个不可达。**

不可达的那部分大多在意料之中——测试替身、离线评测工具、fixture。除了最大的两组，那是**两个完整的环境
provider**。九个模块和十个模块。建好了、测过了、跨版本精炼过，而在这个二进制能触及的范围之外。

还有一个六个版本都建在上面的 fold——世界漂移、身份漂移、premise、按声明目标限定——**没有任何调用者**。四个
报告渲染器也没有，其中三个在自己的 docstring 里点名了一个命令。**那个命令不存在。** 这棵树声明了一个二进制，
而它是个没有子命令的守护进程。

这一切都不是缺陷。阶段文档的标题里就写着这个阶段是一个纵切。限制是真的、刻意的、被记录的——**记在一份文档
里，而不在读者会遇到代码的地方**。这本身是一个发现，而且是同一个发现的两次：一个**声明了没实现**的平面和
一个**实现了到不了**的平面是相反的状态，而两者都没有在任何人会看的地方说明自己。

### 一把尺子，因为「它能用」有七种意思

我最后需要的词汇：

| 层 | 成员判据 |
|---|---|
| **已声明** | 类型存在 |
| **已实现** | 存在会做这件事的代码 |
| **被测试触及** | 有测试调用它 |
| **导入可达** | 在从二进制入口出发的模块图里 |
| **被组合** | 在 composition root 被实例化 |
| **可采纳** | 能成为一次运行绑定的那个东西 |
| **可共存** | 能和另一个**一起**用于同一次运行 |

每一层都是工作可以停下、而看起来像完成了的地方。一套绿色测试证明的是第 3 层。它对第 5 层一个字都没说——
而两个完整的 provider 就坐在这两层之间的缝里。

最后那一层是我出发时没有的，也正是最要紧的那一层。

### 墙不在我标的位置

我写过一份架构笔记，列出当前状态和「两个 provider 的运行」之间的三堵墙：写死的 composition root（接线）、
单数的 surface 选择器（设计）、以及 loop 深处那条拒绝——它会驳回任何针对「本次运行未绑定的 session」的请求
（语义）。

我把重量押在第三堵上。它的论证很好——那个绑定是*「一个关于这次运行是为哪个世界服务的事实，一个在 goal 被
看见之前就由装配决定的事实」*——而跟它争论看起来才是难的部分。

然后我不去争论，改去测量。两个 provider 开在同一棵工作树上，经过真实的 host：

```
filesystem.calls  = ['sessionOpen:workspace', 'sessionClose:release', 'shutdown', 'exit']
repository.calls  = ['shutdown', 'exit']
```

第二个 provider 被注册、被排空，**从头到尾没被说过一句话**——连握手都没有。它不是**被拒绝**了一个 session。
它从来没有被**提供**过一个。

所以那堵语义墙是够不着的。根本没有东西能让第二个 session 去绑定，而一份开篇就去和那条拒绝争论的架构文档，
会是在跟错的文件争论。真正的墙在 boot，往上一层，而且无聊得多——**这恰恰是它需要被测量而不是被推理的原因**。

### 一个计数器不是对世界的描述

我学到的最尖锐的一条，来自那个卡住其它一切的问题。

每个 provider 为自己的 session 维护一个单调 revision，而一个动作的新鲜度是对着它检查的。当两个 provider
作用于同一个目录时，那会变成一个时钟还是两个？

我以为会找到一个健全性 bug——一个 session 的 basis 被拿去和另一个的计数器比。**没有。** 每一处比较都已经先
解析 session，而其中一道门在解析不出来时直接拒绝，理由明写：*「它的 revision 无法与任何东西比较。」* 代码
比我的笔记假设的更小心——**而我是靠去查才知道这一点的，不是反过来。**

真正的问题在上一层，而且两个 provider 都没有隐瞒。各自诚实地写了自己的范围——文件系统*「不监视这棵树，
所以它只宣告自己施加的变化，别无其它」*，仓库的事件范围是 `none`、*「truthfully」*。**没有任何文件说过的，
是这两个诚实的范围合起来是什么：**

> 一个 revision 记录的是**它自己那个 provider 做了什么**。只有一个 provider 时，这和「对世界的描述」无从
> 区分，因为唯一的 provider 就是唯一的行动者。有两个时，一个 basis 可以按自己的计数器是新鲜的，而事实上
> 已经陈旧。

这条超出这个系统。任何带 per-component 计数器的分层系统都有它：**那个计数器是一份本地动作的日志，穿着全局
状态的外衣**，而这层伪装只在第二个行动者出现时才失效。

随之而来的决定：revision 保持 per-component，**永不聚合**。两个数着不同东西的计数器，取最大值或求和都是一个
没有任何东西能兑现的数字。跨 provider 的新鲜度改成了一个**身份**问题——比对「效果声称的」和「一次读取发现
的」——而那正是漂移机制早就在回答的，也正是几个更早的发现从「玩物」变成「输入」的地方。

### 最后真正发出去的东西

daemon 现在在一棵工作树上组合两个 provider。一个声明的世界：文件系统是锚，仓库是**证人**——被询问，从不被
锚定，因为锚在它上面需要的正是刚刚被拒绝的那种聚合。

而接线里有意思的部分不是接线。在非 checkout 的目录里，仓库 provider 广告零个 surface，而一个「证人无法被
采纳」的世界会整体失败——所以无条件声明它的 daemon **在普通目录里会拒绝启动**。装配的做法是**去问** provider，
而不是在那个已经能回答这个问题的东西旁边，再实现一遍 git 检查。

那次提交让三个 pin 变红：可达性遍历、一条关于旧组合方式的断言、以及一条说「这对 provider 是本 runtime 组装
不出来的」。三条都是**带理由更新**，不是删掉。**一个 pin 在它被写来捕捉的那次改动上变红，就是这个 pin 在
工作。**

其中一条有个洞，而正是这次改动把它暴露出来：它断言 provider 源码里**存在**一句状态标记。接线之后，那句话
变成了**假的**——而测试照样通过。

**存在不等于为真**，这件事后来自成一个题目。
