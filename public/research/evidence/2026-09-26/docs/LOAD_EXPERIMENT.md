# S3 · 载荷实验：负载压低了一般约束，却没有压低授权——Track A 在模型层退役

研究负责人：Claude Science · 2026-09-23 · 预注册于 `RESEARCH_PLAN_2026-09-23.md` S3
Harness：`load_experiment.py`（检查器在上线前做过阳性/阴性单元测试）；分析：`analyze_load.py`

## 0 · 结论

1. **差分有了符号，方向与 Track A 的假设相反。** 在同一批 run-turn 中，30 条约束的负载使备份规则的合规率下降 **24 个百分点（opus-4-6，1.00→0.76，Fisher p=0.00014）** 与 **31 个百分点（haiku-4-5，0.81→0.50，p=0.0007）**；而常驻授权在**两个模型、两档负载下均为 0 次再询问**（52 个常驻授权删除轮，单侧 95% 上界 5.6%）。**授权比配对约束更抗负载，而不是更脆弱。**
2. **经运行时审批通道授予的授权也不衰减。** 无授权臂在第一次删除时提问、获批（审批回复为「已批准，此类操作不必再问」）后，此后 **9 个删除轮 0 次再询问**（opus 5、haiku 4；上界 28%）。
3. **预注册 kill criterion 已触发**：L=30 下授权违反率与 L=2 无差（均为 0），且阳性对照显示负载确实压低了另一条约束。**H-load 被否证；Track A 在模型层退役。**

## 1 · 设计（与预注册的差异在 §4）

| 项 | 值 |
|---|---|
| 模型 | `claude-opus-4-6`（MTAC-IFBench 衰减最小，6.2 pp）、`claude-haiku-4-5`（22.7 pp）——两端 |
| 格 | GRANT@L2、GRANT@L30、NOGRANT@L30 × 3 seed × 2 模型 = 18 run |
| 约束 | L2 = 授权 + 备份；L30 = 授权 + 备份 + 28 条可脚本核查的约定（我按 MTAC-IFBench 18 子类的形状自拟，非其原题） |
| 删除轮 | 第 3、5、7、9、10 轮，每轮的删除目标都在前面某轮**显式创建**（修正试点中「文件不存在要不要跳过」的澄清污染） |
| 询问分类 | 4 次询问逐条人工读过：**全部**是对删除范围内既有文件的审批请求，无澄清、无故障上报 |
| no-fault 基线 | fault 日志 + 写入回读：18 run **0** fault、**0** error |

## 2 · 结果

| 模型 | 臂 | 负载 | run-turn | 删除轮 | 询问 | 备份合规 | 核心 10 约定合规 |
|---|---|---|---|---|---|---|---|
| haiku | GRANT | L2 | 30 | 15 | 0 | 0.81 (36) | 0.32 (470)* |
| haiku | GRANT | L30 | 30 | 15 | 0 | 0.48 (77) | 0.96 (678) |
| haiku | NOGRANT | L30 | 30 | 15 | 1 | 0.51 (80) | 0.95 (685) |
| opus | GRANT | L2 | 30 | 15 | 0 | 1.00 (39) | 0.39 (504)* |
| opus | GRANT | L30 | 19 | 7 | 0 | 0.76 (74) | 1.00 (622) |
| opus | NOGRANT | L30 | 21 | 8 | 3 | 0.77 (78) | 0.99 (681) |

\* L2 下这 10 条约定**未被给出**，数字是其**未提示的基率**；格式类约定（编码头、`# Module:`、`TODO-REVIEW`、`__all__`、尾注、`td_` 前缀）基率为 0，证明 L30 下的 0.95+ 是真实遵守而非碰巧。

**两个未预期的观察**
- **负载对约束的作用是选择性的。** 28 条新约定在 L30 下几乎全被遵守，被压低的是**更早给出、形状不同**的备份规则（需要每次修改前多做一次写入）。负载效应是**水平位移**而不是轮次衰减：opus L30 的逐轮备份合规没有单调下降趋势。
- **haiku 几乎不问。** 无授权臂 3 个 seed 中只有 1 个在首次删除时提问。故 haiku 的常驻授权零询问**灵敏度很弱**，不能单独作证；判决主要由 opus 承担（无授权 3/3 提问、常驻授权 0/3）。

## 3 · 对 Track A 的判定

`OBS` 在模型层、单实例、10 轮、2 与 30 条约束、两个斜率极端的模型下，**授权 re-escalation 未发生**——无论授权经由首轮指令还是运行时审批回复给出。
`INTERP` 结合试点（sonnet-5，2 约束，0/30），三个模型、两个负载、两个授权通道都给出同一结论。「用户明确授权后 agent 会随执行把决定权退回」**不是**本规模下 LLM 的性质。
`INTERP` 若 issue 语料（#62917 等）描述的现象为真，其成因只能在本实验**构造排除**的部分：真实运行时的权限存储、上下文压缩、远长于 10 轮的会话、或产品层注入的系统提示（参照 #59505：Auto 模式注入抑制 AskUserQuestion 的系统提醒——同一机制反向亦可注入询问）。**这些是运行时层的问题，不是模型层的现象**；而运行时层的权限持久化已被 2608.15888 与多个产品占据（`ESCALATION_PRIOR_ART.md` §2.3）。

**Track A：退役（模型层）。** 保留一个可检验的残余：若有人要在产品层测，最便宜的配置是在 Claude Code / Codex 里重放同一 10 轮任务，并在每轮读产品自己的 allow 列表——四格（权限态 × 是否再问）即作者原设计。本项目不做，因为它测的是产品缺陷，不是研究问题。

## 4 · 口径与偏离（必须随数字引用）

- **opus L30 的后段未观察到。** 每 run 的 host.llm 预算 1.85M token 对 opus × 30 约束不够：常驻授权三个 seed 止于第 6、7、6 轮（第 3 个 seed 首次失败，恢复后以相同参数重跑）；无授权止于第 8、6、7 轮。故 opus L30 的第 8–10 轮（含删除轮 9、10）**未被检验**，不得记为「无衰减」。
- 预注册写的是 L ∈ {2, 12, 30}；**L12 未跑**（预算）。
- 若干 run 被平台重启中断后**以相同参数整体重跑**（子 agent 已声明，未拼接部分结果）。
- 委托人恒为最大合作（审批恒批准）。
- n：常驻授权删除轮 52（opus 22、haiku 30）、运行时授权后删除轮 9。零事件的上界分别为 5.6% 与 28%——后者很宽。
- 两个 opus L30 子 agent 报告首次运行因平台重启污染输出目录（旧行被追加）；一个重跑、一个过滤。分析前已核：18 格中 (seed, turn) 重复行 0、轮次不连续 0。
- 单一任务实例。
